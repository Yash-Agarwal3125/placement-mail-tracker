Fix the all-day <-> timed Calendar PATCH bug stuck on two real interviews

Root-caused live against the real API (not guessed): PATCHing an existing
all-day event's start/end into a timed dateTime -- or the reverse -- fails
with HTTP 400 "Invalid start time." every time, regardless of what else is
in the body (reproduced with a minimal {"start": {"dateTime": ...}} PATCH
against one of the two stuck events). This has silently broken the
Tredence and Valco Melton Engg. interview events since the real interview
time arrived in a follow-up mail after each was first created as an
all-day (date-only) event: every sync since has hit this 400, been caught
by the generic per-event exception handler, logged a warning, and moved on
-- both events have been showing the wrong, date-only time on the user's
real calendar for days.

Fixed in _handle_patch: when the stored event's all_day flag disagrees
with the newly-derived event's, delete the stale event and insert a fresh
one instead of attempting the PATCH Google's API rejects for this specific
transition -- sidesteps the undocumented type-conversion restriction
entirely rather than chasing its exact semantics.

Added two regression tests (all-day->timed and the reverse) asserting the
delete+insert path is taken and PATCH is never called for this transition.
700 passed, ruff clean.
